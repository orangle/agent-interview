# 个人项目经验映射

这个文件不是项目简历，而是把已有工程经历映射到 Agent 面试题中，避免回答停留在概念层。

## 背景定位

个人优势不是大模型训练，而是：

- DevOps / CI/CD / 平台工程经验；
- Jenkins、容器、Kubernetes、日志和发布链路；
- 正在建设 Coding Agent / CI/CD 故障诊断 Agent；
- 参与 Claude Code 类交互平台、Sandbox 和 Agent Runtime 设计；
- 对企业系统的权限、稳定性、可观测性和交付流程有真实经验。

面试表达应定位为：

> 具备成熟平台工程经验，正在把传统确定性平台能力与 LLM 的非确定性决策能力结合，转向 Agent Engineering。

不要包装成已经完成大规模商业化 Agent 平台；没有数据支撑的部分必须说明仍处于设计、原型或验证阶段。

## 项目一：CI/CD 故障诊断 Agent

### 业务问题

发布失败根因分散在：

- Jenkins 构建记录；
- 编译和启动日志；
- 代码 Diff；
- 配置和依赖；
- 容器、Pod 和运行环境；
- 网络与外部服务。

传统规则系统能够覆盖高频已知错误，但长尾异常组合多，规则和提示词会持续膨胀。

### 适合映射的面试题

- Agent 和 Workflow 如何选择；
- ReAct 为什么有效；
- Context Engineering；
- Tool Calling；
- Agent 如何停止；
- Agent Evaluation；
- 如何设计 Agent Runtime。

### 架构表达

```text
用户 / 发布任务
      ↓
任务入口与权限校验
      ↓
Agent Runtime
      ├─ 状态、预算、超时、Trace
      ├─ 日志分析工具
      ├─ Jenkins 查询工具
      ├─ Git Diff 工具
      ├─ 环境状态工具
      └─ 知识检索工具
      ↓
根因、证据、不确定性、修复建议
      ↓
高风险操作进入人工审批
```

### 核心取舍

#### Workflow 与 Agent

- Workflow：固定完成任务信息、日志、代码和环境数据采集；
- Agent：根据观察动态决定下一步分析路径；
- 人工/策略：控制重启、回滚、修改配置等高风险动作。

#### Context

不能把完整日志、源码和全部排查手册一次塞给模型。

更合理：

1. 脚本先构建时间线和异常链；
2. 保留原始日志文件；
3. Agent 按假设读取关键前后文；
4. 结构化保存已确认事实、候选根因和未验证项；
5. 阶段结束后压缩，但保留原始引用。

#### 停止条件

完成结果至少包含：

- 失败阶段；
- 第一关键异常；
- 根因或候选根因；
- 支撑证据；
- 置信度和剩余不确定性；
- 下一步建议。

连续步骤无新增证据、缺少权限或达到预算时，返回 partial / blocked，而不是继续猜测。

#### 评估

- 根因被人工确认的比例；
- 第一关键异常定位准确率；
- 证据是否支持结论；
- 重复日志读取率；
- 30 秒或目标时限内完成比例；
- Token 和工具调用成本；
- 越权操作率必须为零。

### 面试中不要说

- “已经能自动修复所有发布问题”；
- “准确率很高”但没有评估集和数字；
- “Agent 自己决定是否重启生产”；
- “把所有日志交给大模型分析”。

## 项目二：Claude Code 类企业交互平台

### 业务问题

企业内部需要让用户通过会话驱动 Coding Agent：

- 获取和修改代码；
- 执行命令、构建和测试；
- 与 Git、Jenkins、内部平台集成；
- 保存会话与工作区；
- 提供 Diff、预览、部署和状态反馈。

### 适合映射的面试题

- 如何设计 Coding Agent；
- Sandbox 和 Runtime；
- 长任务 Context 管理；
- 会话、工作空间和临时代码的关系；
- Agent 中断与恢复；
- 多用户并发和成本隔离；
- Tool / Skill / MCP 的边界。

### 核心对象

```text
Session：用户交互和任务目标
Workspace：代码、文件和执行状态
Runtime：Agent 循环与工具调度
Sandbox：隔离的执行环境
Artifact：Diff、日志、构建结果和预览
Deployment：一次可追踪的发布尝试
```

不要把 Session 和容器绑定为同一个对象：

- 会话可能暂停；
- 容器可能回收；
- 工作区需要持久化；
- Runtime 可以重新创建并恢复任务。

### Context 问题

真实遇到过 Prompt 过长：

- 大量历史对话；
- 工具输出；
- 源码和日志；
- 巨型 Skill / Prompt；
- 多轮失败后的重复信息。

可表达的改进方向：

- Skill 按需加载；
- 工具结果保存为 Artifact，只把摘要和引用放入上下文；
- 任务阶段摘要；
- 结构化状态替代自然语言历史；
- 源码按符号、路径和调用关系检索；
- 上下文预算和压缩触发器；
- 压缩后保留目标、约束、关键决策和未完成事项。

### 可靠性问题

- Agent 进程退出后如何恢复；
- Sandbox 停止后工作区是否还在；
- 工具调用是否幂等；
- 多用户资源和费用如何隔离；
- 旧镜像会话如何升级；
- 长时间任务如何回传状态；
- 用户取消后如何停止正在执行的命令。

这些问题比“用了哪个 Agent 框架”更能体现平台工程能力。

## 项目三：OpenSandbox / Agent Runtime 迁移设计

### 业务问题

现有不同 Agent 场景各自维护运行环境，导致：

- 生命周期不统一；
- 代码和产物处理方式不同；
- 与平台交互协议分散；
- 资源回收、恢复和观测困难；
- 新场景迁移成本高。

目标是抽象统一运行边界：

```text
Control Plane
  ├─ Session / Task
  ├─ Runtime Scheduling
  ├─ Policy / Quota
  └─ Trace / Artifact
        ↓
Sandbox Runtime
  ├─ Workspace
  ├─ Agent Process
  ├─ Tools / Skills
  └─ Build / Test / Preview
```

### 适合映射的面试题

- Agent Runtime 是什么；
- Agent 平台与普通微服务平台有什么区别；
- 状态如何持久化；
- 容器停止后如何恢复；
- 多租户隔离；
- 如何抽象不同 Agent 场景；
- Agent 可观测性。

### 可强调的第一性原理

运行时需要统一的不是某个框架 API，而是以下不变量：

- 任务生命周期；
- 状态和工作区；
- 工具执行；
- 权限与资源；
- 产物和证据；
- 中断、恢复和取消；
- Trace 与评估。

具体模型、Agent 框架和工具协议可以变化，但这些边界长期存在。

## 通用 STAR 表达模板

### Situation

说明真实业务问题和原方案瓶颈，不要一开始堆技术名词。

### Task

说明自己负责的范围：设计、实现、验证或推动，不夸大团队成果。

### Action

重点讲三类判断：

1. 为什么选择 Agent 或 Workflow；
2. 如何控制不确定性；
3. 如何用指标验证。

### Result

有真实数据写数据：

- 时延；
- 成功率；
- 人工耗时；
- 覆盖场景；
- 成本。

暂时没有数据时，应说：

> 当前处于原型/验证阶段，已经完成哪些能力，下一步用什么评估集和指标验证。

不要编数字。

## 面试回答的统一主线

可以在不同题目中反复使用，但不要机械背诵：

> 我做 Agent 系统时最关注的不是如何调用模型，而是如何把模型的不确定性放进一个可控工程系统。确定的数据获取、权限、状态和审批由平台保证；模型负责难以穷举的分析和决策；每一步都有工具协议、预算、Trace 和终止条件；最终通过真实任务成功率、证据质量、时延、成本和安全指标验证。
